# Any Retry 总体开发指南

状态基准：2026-10-22。本文是新项目的开发基线；除明确标为“已确认”或“当前仓库事实”的内容外，架构、字段和目录均是拟定方案，尚未实现。

## 1. 目标与事实基线

**已确认的目标：构建通用重试核心，后续通过适配器接入不同工具。** 首先解决“什么时候可以重试、怎样限制重试、如何确认结果”，再增加具体工具接入。

初次整理开始时，仓库仅有 `.git`。当前已建立文档基线并保留项目级 Understand-Anything 技能；生成地图已移除。这些辅助能力不等于重试引擎，不计入真实工具重试能力。

当前进度以 [STATUS.md](STATUS.md) 为准。未来讨论进度时必须同时说明：

- **目标**：希望最终达到的行为。
- **已实现**：有对应源码或实际文件的内容。
- **实现原理**：实际调用关系；只有设计时必须写“拟定”。
- **可用性**：已验证到什么层级、适用版本及剩余限制。

## 2. 首版范围

### 2.1 计划纳入

- 单机、单服务实例；同一任务只允许一个在途执行。
- 可插拔适配器协议，以及完全离线的模拟适配器。
- 标准化失败事件、有限次数重试、固定等待或指数退避策略。
- 任务状态机、暂停、恢复、停止、人工处理入口。
- 结构化日志、尝试记录和可检查的本地状态。
- 简单命令行控制；首个真实适配器在核心稳定后接入。

### 2.2 暂不纳入

- 分布式调度、多用户协作、云托管和账户权限系统。
- 自动切换供应商、密钥、模型或绕过目标工具限制。
- 自动确认权限、自动处理登录验证或无限重试。
- 自动重跑任意命令、以宽泛文本匹配判断所有错误。
- 默认图形界面、自动启动后台监控、自动接管现有会话。
- “恰好一次执行”保证：没有目标端幂等或可查询能力时，无法仅靠本地记录作此承诺。

这些是控制首版复杂度的建议边界；调整时应记录原因与新的验收条件。

## 4. 架构职责与调用过程（拟定）

| 模块 | 职责 | 不应承担 |
| --- | --- | --- |
| 适配器 | 识别目标、观察工具状态、归一化事件、提交一次操作、声明能力 | 自己启动无限重试或修改全局策略 |
| 核心状态机 | 消费事件、检查合法迁移、决定下一状态 | 直接读取工具私有数据库或操作界面 |
| 策略层 | 分类结果、次数与时限检查、等待时间计算 | 执行工具命令或凭模型猜测成功 |
| 调度层 | 等待、取消和到期触发 | 等待结束后跳过状态复核直接提交 |
| 存储层 | 原子记录状态、尝试及审计事件 | 把本地写入成功当成目标工具执行成功 |
| CLI | 创建任务、查看状态、暂停、恢复、停止 | 隐式开启未授权任务 |

计划调用顺序：

1. 用户指定适配器、目标和重试策略；适配器验证目标身份与支持能力。
2. 观察器生成标准事件，核心按事件标识去重并核对运行身份。
3. 成功事件进入成功状态；不可重试错误终止；未知或人工相关情况暂停处理。
4. 可重试失败经预算与风险检查后进入等待状态，记录下一执行时间。
5. 等待到期后重新确认任务仍可重试、没有人工接管、目标未恢复成功。
6. 写入唯一尝试记录和提交意图，再调用适配器提交。
7. 提交确认只表示已受理；继续观察同一次运行的最终结果。
8. 结果与提交状态不明时，查询或人工确认，不能因为超时就重新发送。

核心不规定工具必须是 CLI、桌面软件还是 HTTP 接口。每种适配器必须独立证明其观察和提交方式可靠。

## 5. 任务、事件与策略契约（拟定）

| 对象 | 最小字段 | 约束 |
| --- | --- | --- |
| Task | `task_id`, `adapter_id`, `target_ref`, `state`, `policy`, `version` | 身份不随重试变化；版本用于避免旧状态覆盖新状态 |
| Event | `event_id`, `task_id`, `run_id`, `kind`, `occurred_at`, `source`, `details` | 去重；事件必须归属于已知任务与运行 |
| Attempt | `attempt_id`, `task_id`, `retry_index`, `status`, `started_at`, `finished_at`, `submission_ref` | 每次提交意图有唯一标识；未知结果保留证据 |
| Policy | `max_retries`, `max_elapsed_seconds`, `delay_mode`, `base_delay_seconds`, `max_delay_seconds`, `attempt_timeout_seconds` | 参数有限且有效，不允许负值或无限预算 |
| Capability | `observe`, `submit`, `query_submission`, `cancel`, `idempotency` | 显式声明，不支持的能力不得假装成功 |

`max_retries` 仅统计初始执行之后的自动重试，避免“总尝试次数”歧义。初始任务由谁发起必须由适配器声明：接管已有运行，或启动一个新运行；同一任务不能隐式混用。

每个新的重试提交意图先消耗一个重试名额，恢复后对同一 `attempt_id` 的状态查询不重复消耗。发生提交歧义时保留该名额，不回退计数后再次盲发。

首版建议默认不重试，要求用户显式启用并设置预算；演示用有限预算只是示例，不作为生产参数。时间戳存储使用 UTC；进程内时长使用单调时钟。恢复时校验持久化截止时间，不延长原始总预算。

## 6. 适配器接口与接入要求（拟定）

建议接口职责如下，具体语言签名在协议实现阶段确定：

| 接口 | 输入 / 输出约定 |
| --- | --- |
| `validate_target(target_ref)` | 返回明确身份、版本和能力，或给出不可用原因 |
| `observe(target_ref, cursor)` | 返回标准事件及新游标；说明断线、重放、丢失事件的处理方式 |
| `submit_retry(target_ref, attempt_id, action)` | 返回受理、拒绝或结果未知，以及可查询的提交标识 |
| `query_submission(submission_ref)` | 在支持时返回在途或最终结果；不支持时明确返回能力缺失 |
| `cancel(submission_ref)` | 返回取消请求的结果；未确认取消前不得宣称执行已停止 |

适配器接入清单：

- 明确目标版本、接口来源、会话或进程标识，以及操作授权范围。
- 给出成功、失败、运行中、人工输入、权限请求和连接中断的可复现样例。
- 定义哪些错误可重试，哪些必须人工处理，哪些永久失败。
- 明确重复执行是否安全，以及 `attempt_id` 是否能映射为目标端幂等键。
- 同时提供模拟契约测试和真实工具验收记录；模拟通过不代表真实接入成功。
- 不将“发送继续”等特定工具行为固化进核心；它应是适配器明确支持的操作。

## 7. 状态机与控制语义（拟定）

| 状态 | 含义 | 主要后续状态 |
| --- | --- | --- |
| `READY` | 已验证目标，等待启动或绑定运行 | `RUNNING`, `PAUSED`, `STOPPED` |
| `RUNNING` | 目标运行在途或正在观察结果 | `SUCCEEDED`, `WAITING_RETRY`, `FAILED`, `NEEDS_ATTENTION`, `PAUSED`, `STOPPED` |
| `WAITING_RETRY` | 已批准重试，等待执行时间 | `RUNNING`, `SUCCEEDED`, `FAILED`, `PAUSED`, `STOPPED`, `NEEDS_ATTENTION` |
| `PAUSED` | 禁止新提交，等待用户恢复 | 恢复时重新验证后进入 `RUNNING` / `WAITING_RETRY`；也可 `STOPPED` 或 `NEEDS_ATTENTION` |
| `NEEDS_ATTENTION` | 提交结果不明、身份变更或需人工介入 | 核实后决定 `RUNNING`, `WAITING_RETRY`, `SUCCEEDED`, `FAILED`, `STOPPED` |
| `SUCCEEDED` | 适配器确认目标工具执行成功 | 终态 |
| `FAILED` | 永久错误、预算耗尽或明确失败终止 | 终态 |
| `STOPPED` | 用户要求停止自动重试 | 终态 |

暂停和停止阻止新的提交，但不自动等于取消已发送的执行。若需要取消，调用独立取消能力并展示结果。终态之后的迟到事件保留审计记录，不触发自动复活。

暂停期间继续记录观察事件；恢复时先查询最新状态，再决定是否等待或继续观察。状态写入、取消意图及提交门禁需要串行化，防止“用户已停止但定时器仍发送”的竞争。

事件处理优先级：停止或人工接管意图优先于新的重试提交；成功结果使旧失败和旧定时器失效；过期运行的事件不影响当前运行。启动新任务需要新的 `task_id`。

## 8. 失败分类与重试策略（拟定）

| 分类 | 默认行为 | 需要的证据 |
| --- | --- | --- |
| 明确的临时错误 | 预算内重试 | 适配器确认错误可重试且重复操作安全 |
| 限流 | 按目标建议等待并检查总期限 | 可识别的限流事件与等待提示 |
| 身份认证、权限或配置错误 | 进入人工处理或明确失败 | 错误码和脱敏原因 |
| 用户取消、人工输入或会话变化 | 停止或暂停 | 可归属的用户或会话事件 |
| 提交后断线、结果未知 | 查询；无法确认时人工处理 | 提交意图、提交标识及最后可确认事件 |
| 未识别错误 | 不自动重试 | 保留原始错误摘要供后续分类 |

指数退避建议为 `min(max_delay, base_delay * 2^(retry_index - 1))`，可附加有界抖动；`retry_index` 从 1 开始。实际等待需考虑目标端最小等待要求，且不得超过任务剩余总时限；若无法满足，就终止或等待人工处理。固定间隔作为可选策略。

运行超时不直接等同于失败：目标可能仍在执行。适配器确认失败或确认取消后才能继续判断重试资格。测试必须注入时钟与随机源，避免真实长时间等待。

## 9. 存储、恢复与数据边界（拟定）

- 建议使用 SQLite 原子保存任务、尝试与去重事件；首版限制一个服务实例持有执行权。
- 外部提交和本地事务不能合并成原子操作。先持久化提交意图，崩溃后查询目标；无幂等与查询能力时进入人工确认，不声称恰好一次。
- 重启后不得直接重发所有未完成任务。对在途或提交未知的任务先恢复观察，对等待任务先核对身份、预算和停止标记。
- 持久化存储失败时禁止继续提交，避免没有记录的执行。
- 日志至少包含任务、尝试、事件、时间、状态迁移、判定原因与耗时；默认不记录完整提示词、响应正文或凭据。
- 运行数据保存在被 Git 忽略的本地目录；提交验收证据前先脱敏。
- 若未来增加 Web 控制台，再独立设计本地监听、请求来源校验、操作鉴权和关闭服务流程；这些功能当前均不存在。

| P4 扩展 | 第二个适配器或可视控制台 | 核心复用，旧行为无回归 | 未开始 |

### 核心必测场景

1. 首次成功不重试；临时失败后成功，次数准确。
2. 连续失败耗尽预算；固定间隔与退避等待计算正确。
3. 永久错误、未知错误和人工介入不自动重发。
4. 等待中暂停或停止，到期无新提交；迟到失败不复活任务。
5. 重复事件只消费一次；旧 `run_id` 不污染新运行。
6. 提交前后崩溃、受理响应丢失、查询不支持，均不盲目重复提交。
7. 同任务重入不产生两个在途提交；存储故障阻止提交。
8. 总时间预算耗尽、参数无效、重启后截止时间已过，均有明确终止原因。
9. 暂停时目标已成功，恢复后直接确认成功，不继续重试。

### 验证层级

| 层级 | 能证明 | 不能证明 |
| --- | --- | --- |
| 文档与静态检查 | 文件、链接及设计记录一致 | 程序可运行 |
| 单元与模拟测试 | 指定场景下核心逻辑符合预期 | 真实工具兼容性 |
| 本地集成测试 | 存储、调度与 CLI 协作 | 上游接口长期稳定 |
| 真实适配器验收 | 指定版本、指定环境与场景可用 | 任意工具、任意错误都可重试 |
| 业务验收 | 明确验收标准下目标完成 | 所有后续任务必然成功 |

当前没有重试引擎的自动化测试命令。首次实现引擎时应加入实际执行成功的安装、测试、启动和停止命令，并注明环境。

## 12. 后续开发与文档维护

开始开发时先阅读 README → STATUS → 本指南，再检查实际源码和测试；若代码与本文冲突，以源码确定当前实现，并将差异记录为设计决策，而不是默默覆盖。

每项能力从“设计”改为“已实现”时，需要附源码路径与关键符号；改为“已验证”时，还需要测试命令、结果、日期、环境和已知限制。真实接入的验收记录建议放在 `docs/acceptance/`，只保存脱敏证据。

调整状态、事件、策略或适配器协议时同步修改契约测试和本文；调整使用方式时同步修改 README；进度变化统一更新 STATUS。同一次重试完成不代表用户的业务任务已经完成。
